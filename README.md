# artcation 회원 인증 설계 (발췌본)

공연 아티스트와 호스트를 연결하는 팀 프로젝트 **artcation**에서 제가 맡은 회원 인증(USR-AUTH) 설계 문서입니다.
원본은 팀의 private 저장소에 있으며, 본인 담당 부분만 발췌해 구성했습니다. 프로젝트는 진행 중입니다.

- **API 계약 보기:** [Swagger UI](./index.html)
- **담당 범위**
  - 설계: 인증 도메인의 intent·spec·OpenAPI 계약 초안 작성, 이후 팀 리뷰를 거쳐 함께 다듬음
  - 구현: 로그인 토큰 발급, 로그아웃 폐기, Access Token 재발급(Refresh Token Rotation), 비밀번호 변경 시 세션 무효화

> 수록한 문서는 팀 리뷰가 반영된 최종 버전이라, 일부 문구는 팀원이 수정한 내용을 포함합니다.

## 작업 방식

Claude와 함께 문서를 단계별로 구체화한 뒤, 그 문서를 기준으로 구현했습니다.

| 단계 | 산출물 | 내용 |
|---|---|---|
| Plan | [`intent/USR-AUTH.md`](./intent/USR-AUTH.md) | 문제와 원하는 결과 정의 |
| Design | [`spec/USR-AUTH-token.md`](./spec/USR-AUTH-token.md) | 트리거·처리 로직·예외 케이스로 구체화 |
| Contract | [`openapi.yaml`](./openapi.yaml) | spec 확정 후 API 계약으로 옮김 |

확실하지 않은 내용은 본문에 채우지 않고 열린 질문으로 남기며, 예외 케이스가 빠진 spec은 완성으로 보지 않았습니다.

## 초안을 그대로 쓰지 않은 이유

**이메일 인증 시점: "가입 후 인증" → "인증 후 계정 생성"**

intent 초안을 Claude와 작성하던 단계에서, 첫 제안은 계정을 먼저 만들고 이메일 인증을 나중에 받는 방식이었습니다.
이 방식은 미인증 계정의 로그인 범위, 방치 계정 삭제 주기, 재가입 충돌 처리처럼 예외 정책이 계속 늘어났습니다.
그래서 인증을 마친 이메일만 계정을 만들도록 바꾸고, 인증 상태는 Redis에 TTL로 임시 저장했습니다.
이때 도입한 Redis는 Refresh Token 저장소로도 재사용했습니다.

**회원가입 신원 확인: "요청에 담긴 이메일" → "인증 완료 쿠키"**

인증 후 계정을 만드는 구조였지만, 회원가입 요청은 여전히 이메일을 본문으로 받고 있었습니다.
서버는 그 이메일이 인증된 상태인지만 확인할 수 있었고, 요청을 보낸 사람이 실제로 인증한 사람인지는 알 수 없었습니다.
그래서 다른 사람이 방금 인증한 이메일을 본문에 넣으면, 인증 유효시간 10분 안에 그 이메일로 가입할 수 있었습니다.

이메일을 요청 본문에서 빼고, 인증 성공 시 발급한 httpOnly 쿠키(1회용, 10분 TTL)로만 가입 대상 이메일을 확인하도록 API 계약을 바꿨습니다.

## 토큰 핵심 설계

| 항목 | 결정 | 이유 |
|---|---|---|
| 저장 위치 | `httpOnly; Secure; SameSite=Lax` 쿠키 | JS에서 읽을 수 없어 XSS 탈취 방지 |
| 만료 | Access 15분 / Refresh 슬라이딩 2주 + 절대 60일 | 탈취 피해는 짧게, 로그인 유지는 길게 |
| Rotation | 재발급마다 Refresh Token 교체 | 폐기된 토큰 재사용으로 탈취 감지 |
| 탈취 대응 | 폐기 토큰 재사용 시 계정의 모든 세션 삭제 | 누가 썼는지 알 수 없으므로 전체 종료 |
| 동시 요청 | 교체 후 30초 이내 재사용은 409, 세션 유지 | 여러 탭·재시도로 정상 사용자가 로그아웃되는 문제 방지 |
| 저장소 | Redis | 잦은 교체를 TTL로 처리 |
