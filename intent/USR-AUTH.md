# USR-AUTH_intent
작성자: 김다은

**문제**
- 이메일·카카오 회원가입, 로그인, 로그아웃, 토큰 재발급, 비밀번호 재설정, 회원 탈퇴까지 이어지는 인증 플로우가 없다.
- JWT 세션을 발급·재발급하고, Refresh Token을 삭제해 종료하는 체계가 없다.
- 비밀번호를 잊은 회원이 스스로 복구할 방법이 없다.

**원하는 결과**
- 회원이 이메일(추후 카카오도)로 가입·로그인하면 JWT가 안전한 쿠키로 발급되고, 만료 시 재발급된다.
- 로그아웃하면 서버에 저장된 Refresh Token이 폐기되어 더 이상 로그인 상태로 인정되지 않는다.
- 비밀번호를 잊은 회원은 이메일로 재설정할 수 있다.
- 프론트엔드가 사이트 진입·새로고침 시 현재 로그인 상태와 화면 표시용 정보(닉네임 등)를 서버에서 조회할 수 있다.

**구현 기능**

지금 구현
- 이메일 회원가입(약관 동의 포함)
- 이메일 로그인
- 로그아웃
- Access Token 재발급
- 비밀번호 재설정
- 아이디 찾기
추후 구현(기획 미확정 또는 후순위)
- 카카오 회원가입
- 카카오 로그인
- 회원 탈퇴
- 계정 정지(운영 정책 미확정, 확정 시 반영)
- 내 정보 조회(로그인 상태 확인, 미구현)

**영향받는 사용자·시스템**
- 신규 가입자·기존 회원이 주 사용자다.
- users 테이블, Redis(이메일 인증코드·이메일 인증 완료 토큰·Refresh Token·비밀번호 재설정 토큰 저장), 이메일 발송 서비스(SMTP, 발신 주소는 팀 공용 Gmail 계정), JWT 발급·검증 로직, 프론트엔드 회원가입·로그인·비밀번호 재설정 화면이 얽힌다.
- 추후 구현 범위는 추가로 카카오 OAuth API, user_agreements 테이블, 탈퇴 이력 테이블과 얽힌다.

**제약**
- 입력받는 필드는 이메일, 인증코드, 아이디, 비밀번호, 14세 미만 여부, 약관 동의 3개(이용약관, 개인정보 수집 및 이용 동의, 마케팅 정보 수신 동의)다.
- 이메일은 형식 검증을 거친다.
- 인증코드는 CSPRNG로 생성한 영문+숫자 혼합 6자리이며, Redis에 SET EX로 저장한다(기존 코드가 있으면 덮어쓴다). TTL은 10분이다. 재입력 횟수는 우선 무제한으로 허용한다(추후 필요 시 제한 도입 검토).
- 아이디는 4~20자, 영문·숫자·언더스코어만 허용한다(특수문자·공백 금지). 아이디는 유일해야 하며 중복 가입을 허용하지 않는다.
- 비밀번호는 8자 이상 20자 이하, 영문+숫자+특수문자 조합이다(허용 특수문자: !@#$%^&*()_+-=[]{},.<>?).
- 약관 동의는 이용약관, 개인정보 수집 및 이용 동의가 필수이며, 마케팅 정보 수신 동의는 선택이다. boolean 자기 신고 방식으로 users 테이블에 저장한다. 약관 버전 관리 및 동의 시각 기록은 추후 구현한다. 제3자 정보제공 동의는 견적서 발송·공고 게시 시점에 별도로 받는다.
- 인증 완료 후 회원가입을 마쳐야 하는 제한 시간은 10분이다. 인증코드 확인에 성공하면 서버가 별도의 이메일 인증 완료 토큰을 발급해 httpOnly, Secure 쿠키로 전달하고(Redis에 10분 TTL로 저장), 회원가입 완료 요청은 이 토큰으로 검증하며, 가입 성공 시 이 토큰은 즉시 폐기(1회용)한다. 인증코드 자체는 검증 성공 시 즉시 폐기한다.
- 만 14세 미만 가입을 차단한다. 확인 방식은 boolean 자기 신고이며, 실제 생년월일 검증은 하지 않는다.
- JWT는 httpOnly, Secure, SameSite=Lax 쿠키로 관리한다. 쿠키를 프론트 JS에서 읽을 수 없으므로 로그인 상태는 내 정보 조회 API로 확인한다.
- 내 정보 조회 응답에는 닉네임·이메일만 담는다(추후 필요 시 확장).
- Access Token 만료는 15분으로 한다. Refresh Token은 슬라이딩 만료 2주(사용할 때마다 유효기한이 갱신됨) + Rotation(재발급 시마다 새 Refresh Token을 발급하고 기존 토큰은 폐기하며, 이미 폐기된 토큰이 재사용되면 탈취로 간주해 해당 계정의 모든 Refresh Token을 삭제. 단, 교체 후 30초 이내의 직전 토큰 재사용은 동시 요청·재시도로 보고 세션을 유지한 채 거부만 한다)을 적용하고, 최초 로그인 시점 기준 절대 만료 60일(슬라이딩으로 계속 갱신되어도 60일이 지나면 무조건 강제 로그아웃 후 재로그인 필요, 재로그인 시 60일 시계가 새로 시작됨)을 둔다.
- Refresh Token은 로테이션 빈도가 높아 TTL 기반 만료 처리가 유리하므로 Redis에 저장한다.
- 재설정 토큰은 CSPRNG로 생성한 영문+숫자 혼합 6자리이며, Redis에 SET NX EX로 예약해 동시 발급 시 값이 겹치는 경쟁 조건을 방지한다. 이미 존재해 예약에 실패하면 재생성 후 재시도하며, 최대 5회 재시도 후에도 실패하면 500 에러로 처리한다. 유효시간은 30분이다. 재설정 성공 시 해당 토큰은 즉시 폐기(1회용)한다.
- 비밀번호 변경 시 Refresh Token을 전체 삭제해 기존 로그인 세션을 모두 끊는다.
- 계정 존재 여부는 로그인·비밀번호 재설정 응답에서 노출하지 않는다.
- 아이디 찾기는 이메일로 loginId를 발송한다. 미가입 이메일에는 "해당 이메일로 가입된 계정이 없습니다"를 명시한다(사용자가 어떤 이메일로 가입했는지 모르는 상황이므로 열거 공격 우려보다 UX를 우선한다).
- 비로그인 사용자도 사이트 둘러보기(열람)는 가능하므로, 로그아웃 후에는 로그인 페이지가 아닌 홈 화면으로 이동한다.
- Redis를 사용한다.
- 우선 MySQL로 개발하고 추후 다른 DB로 마이그레이션할 수 있다(참고).
- 일정 제약: 2026-10-02까지 완료해야 한다.

추후 구현 관련 제약(참고, 착수 시 재확인)
- 카카오 로그인은 이메일이 아닌 카카오 고유 ID로 회원을 식별한다. 이메일 제공 동의 여부는 로그인 처리에 영향을 주지 않는다.
- 카카오 회원가입 시 이메일 제공 동의를 받지 못해도 가입을 허용한다. 이메일은 온보딩 과정에서 보강한다.
- 카카오 전용 계정은 비밀번호 재설정 대상이 아니며 "카카오 로그인 계정입니다" 안내를 노출한다(카카오 가입 구현 이후에만 해당).
- 약관 버전 관리가 필요해지면 user_agreements 테이블을 별도로 설계한다. 동의 시각 기록도 이 시점에 함께 추가한다.
- 개인정보(이메일·이름·전화번호 등)는 삭제·익명화한다. Soft delete는 다른 데이터가 계정을 참조 중일 때 FK 참조 무결성을 지키기 위한 장치이며, 참조가 없으면 상태값이나 하드 삭제로 충분하다.
- 익명화는 개인정보 파기와 unique 제약 충돌 해소를 동시에 처리한다. NOT NULL+unique 필드는 `deleted_{id}`로, nullable 필드는 `NULL`로 바꾸고 PK는 유지하며, 원본 값을 이어붙이지 않는다.
- 탈퇴 이력 테이블은 soft delete를 대체하지 않으며, 재가입 제한·어뷰징 방지에 필요한 식별자만 해시로 저장한다.
- 소셜 계정은 탈퇴 시 비밀번호 재확인 대신 탈퇴 의사 확인으로 대체한다.

**열린 질문**
- 이용약관·개인정보 처리방침 본문 내용과 버전은 구현 완료 후 작성 예정이다(클라이언트 답변). (약관 동의 착수 시)
- 탈퇴 시 진행 중인 공고·제안 처리 방식(자동 취소 여부 등)을 담당 파트와 협의해야 한다. (회원 탈퇴 착수 시)
- 카카오 인증 완료를 프론트에서 백엔드로 어떻게 전달할지(Authorization Code 플로우 등) 확정이 필요하다. (카카오 가입·로그인 착수 시)
