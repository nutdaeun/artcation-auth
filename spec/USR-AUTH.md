## USR-AUTH-001 이메일 인증코드 발송

**트리거**
회원가입 화면에서 이메일을 입력하고 인증코드 발송을 요청한다.

**사전조건**
- 비로그인 상태다.
- 아직 이메일 인증을 완료하지 않았다.

**입력**
- 이메일 (string, 이메일 형식)

**처리 로직**
- 이메일 형식이 올바른지 확인한다.
- 이미 가입된 이메일인지 확인한다.
- 가입 가능한 이메일이면 CSPRNG로 영문+숫자를 혼합한 6자리 인증코드를 생성해 Redis에 `SET EX`로 저장하고(기존 코드가 있으면 덮어쓴다), 10분 유효시간이 적용된 채로 해당 이메일로 발송한다. 발송 횟수는 `verify:attempts:{email}` 키에 `INCR`로 원자적으로 카운트하며, 발송할 때마다 TTL을 10분으로 갱신한다(슬라이딩). 마지막 발송 시점 기준 10분이 지나야 카운터가 리셋된다. 발송 횟수가 5회를 초과하면 429 에러(`SEND_LIMIT_EXCEEDED`)를 반환한다.

**출력**
인증코드 발송 완료 안내, 인증코드 입력 화면으로 이동.

**예외 케이스**
- 이메일 형식 오류 → 입력 필드에 인라인 에러 표시, 요청을 보내지 않는다
- 이미 가입된 이메일 → "이미 가입된 이메일입니다" 표시, 코드를 발송하지 않는다
- SMTP 이메일 발송 요청 실패 → 이메일 입력 필드 아래 인라인 에러 표시, 재시도 가능
- 10분 내 발송 횟수 5회 초과 → 429 에러, 10분 후 재요청 유도

## USR-AUTH-002 이메일 인증코드 검증

**트리거**
인증코드 입력 화면에서 영문+숫자 혼합 6자리 코드를 입력하고 확인을 제출한다.

**사전조건**
해당 이메일로 발급된 인증코드가 유효 상태로 존재한다.

**입력**
- 이메일 (string)
- 인증코드 (string, 영문+숫자 혼합 6자리)

**처리 로직**
- 입력한 코드와 발급된 코드가 일치하는지 확인한다(인증코드는 발급 후 10분간만 유효).
- 일치하면 인증코드와 발송 카운터(`verify:attempts:{email}`)를 즉시 폐기하고, 해당 이메일의 이메일 인증 완료 토큰을 발급해 Redis에 10분 TTL로 저장한다. 인증 완료 시점부터 10분 안에 회원가입을 마쳐야 하는 제한이 걸린다.
- 재입력 횟수는 제한하지 않는다.

**출력**
인증 완료 처리(이메일 인증 완료 토큰을 httpOnly·Secure 쿠키로 전달), 회원가입 정보 입력 화면으로 이동.

**예외 케이스**
- 코드 형식 오류(영문+숫자 혼합 6자리가 아님) → 인라인 에러 표시, 요청을 보내지 않는다
- 코드 불일치 → "인증코드가 올바르지 않습니다" 표시, 재입력을 허용한다(횟수 제한 없음)
- 코드 만료 또는 존재하지 않음 → "인증코드가 만료되었습니다" 표시, 재발송 유도

## USR-AUTH-003 이메일 회원가입 완료

**트리거**
이메일 인증 완료 후 제한 시간 안에 비밀번호·만 14세 확인을 입력하고 가입을 제출한다.

**사전조건**
- 이메일 인증 완료 토큰(쿠키)을 보유하고 있다.
- 인증 완료 후 10분이 지나지 않았다.

**입력**
- 이메일 인증 완료 토큰 (쿠키, 이메일은 별도로 받지 않고 이 토큰으로 식별)
- 아이디 (string, 4~20자, 영문·숫자·언더스코어만 허용)
- 비밀번호 (string, 8자 이상 20자 이하, 영문+숫자+특수문자 조합, 허용 특수문자: !@#$%^&*()_+-=[]{},.<>?)
- 만 14세 이상 확인 (boolean, 필수)
- 이용약관 동의 (boolean, 필수)
- 개인정보 수집 및 이용 동의 (boolean, 필수)
- 마케팅 정보 수신 동의 (boolean, 선택, 미전송 시 false)

**처리 로직**
- 이메일 인증 완료 토큰이 유효한지 확인하고, 토큰에 연결된 이메일을 가입 대상 이메일로 사용한다.
- 만 14세 이상 확인이 체크됐는지 먼저 확인하고, 미체크(만 14세 미만)면 나이 요건 미충족으로 가입을 차단한다.
- 필수 약관(이용약관, 개인정보 수집 및 이용 동의)이 모두 동의됐는지 확인하고, 미동의 항목이 있으면 가입을 차단한다.
- 아이디 형식을 확인하고, 이미 사용 중인 아이디인지 확인한다.
- 비밀번호 형식을 확인한다.
- 검증을 통과하면 계정을 생성하고, 이메일 인증 완료 토큰을 즉시 폐기(1회용)하며 쿠키를 만료시킨다.

**출력**
가입 완료 처리, 로그인 상태로 홈 화면 이동.

**예외 케이스**
- 이메일 인증 완료 토큰이 없거나 유효하지 않음, 또는 인증 완료 후 10분 초과 → 인증 만료 안내, 이메일 인증부터 다시 진행하도록 유도
- 아이디 형식 오류(4자 미만, 20자 초과, 또는 영문·숫자·언더스코어 외의 문자 포함) → 인라인 에러 표시, 요청을 보내지 않는다
- 비밀번호 형식 오류(8자 미만, 20자 초과, 또는 영문·숫자·특수문자 중 하나 이상 누락) → 인라인 에러 표시("비밀번호는 8-20자의 영문+숫자+특수문자 조합으로 설정해주세요"), 요청을 보내지 않는다
- 만 14세 이상 확인 미체크(만 14세 미만) → "만 14세 미만은 가입할 수 없습니다" 표시, 가입 차단
- 필수 약관 미동의(이용약관, 개인정보 수집 및 이용 동의 중 하나라도 false) → "필수 약관에 동의해주세요" 표시, 가입 차단
- 이미 사용 중인 아이디 → "이미 사용 중인 아이디입니다" 표시, 가입 차단
- 처리 도중 동일 이메일로 이미 가입이 완료된 경우(동시 요청 등) → 가입 차단, "이미 가입된 이메일입니다" 안내
- 처리 도중 동일 아이디로 이미 가입이 완료된 경우(동시 요청 등) → 가입 차단, "이미 사용 중인 아이디입니다" 안내

## USR-AUTH-004 로그인

**트리거**
로그인 화면에서 아이디와 비밀번호를 입력하고 로그인 버튼을 누른다.

**사전조건**
- 비로그인 상태다.
- 이메일 인증이 완료된 계정이 존재한다.

**입력**
- 아이디 (string)
- 비밀번호 (string)

**처리 로직**
- 아이디로 계정을 찾고 비밀번호가 일치하는지 확인한다.
- 탈퇴 상태의 계정은 존재하지 않는 계정과 동일하게 처리한다.
- 인증에 성공하면 Access Token(15분 만료)과 Refresh Token(슬라이딩 만료 2주, 절대 만료 60일)을 발급해 httpOnly·Secure·SameSite=Lax 쿠키로 내려준다.

**출력**
로그인 성공, 홈 화면으로 이동.

**예외 케이스**
- 존재하지 않는 아이디, 비밀번호 불일치, 또는 탈퇴한 계정 → "아이디 또는 비밀번호가 올바르지 않습니다" 표시, 어느 경우인지 구분하지 않는다
- 계정 정지 처리: 정지 정책 자체가 아직 논의되지 않아 이번 범위에서 제외한다(추후 필요 시 정책 확정 후 반영).

## USR-AUTH-005 로그아웃

**트리거**
로그아웃 버튼을 누른다.

**사전조건**
로그인 상태다(유효한 Access 또는 Refresh Token을 보유한다).

**입력**
없음(쿠키의 토큰으로 세션을 식별한다)

**처리 로직**
- 현재 세션의 Refresh Token을 서버에서 즉시 삭제한다.
- 클라이언트의 Access·Refresh Token 쿠키를 만료시킨다.

**출력**
로그아웃 처리, 홈 화면으로 이동.

**예외 케이스**
- 이미 만료되었거나 무효화된 토큰으로 요청 → 오류 없이 로그아웃 상태로 처리한다(멱등 처리)

## USR-AUTH-006 Access Token 재발급

**트리거**
Access Token 만료로 API 요청이 거부된 클라이언트가 Refresh Token으로 재발급을 요청한다.

**사전조건**
만료·폐기되지 않은 Refresh Token을 쿠키로 보유하고 있다.

**입력**
- Refresh Token(쿠키)

**처리 로직**
- Refresh Token이 유효한지, 이미 사용되어 폐기된 토큰은 아닌지 확인한다.
- 유효하면 새 Access Token과 새 Refresh Token을 발급하고 기존 Refresh Token은 즉시 폐기한다.
- 직전에 폐기된 토큰이 교체 후 30초(유예시간) 이내에 다시 사용되면, 동시 요청·네트워크 재시도로 보고 세션을 유지한 채 재발급만 거부한다(새 토큰을 발급하지 않는다).
- 이미 폐기된 토큰이 유예시간이 지난 뒤 다시 사용되면 탈취로 간주해 해당 계정의 모든 Refresh Token을 삭제한다.
- 동시에 같은 Refresh Token으로 여러 요청이 들어오면 하나만 재발급에 성공하고, 나머지는 유예시간 이내 재사용으로 처리한다.
- 최초 로그인 시점 기준 절대 만료 60일이 지났으면, 슬라이딩 만료가 남아 있어도 재발급을 거부한다.

**출력**
새 Access·Refresh Token을 쿠키로 갱신.

**예외 케이스**
- Refresh Token이 슬라이딩 만료(2주)를 지남 → 재발급 거부, 재로그인 요구
- 절대 만료(60일)를 지남 → 재발급 거부, 재로그인 요구
- 교체 후 30초 이내 직전 토큰 재사용(동시 요청·재시도) → "이미 갱신된 토큰입니다" 409, 세션 유지, 이미 갱신된 쿠키로 원래 요청을 다시 보낸다(로그아웃 처리하지 않는다)
- 유예시간이 지난 폐기 토큰의 재사용(탈취 의심) → 재발급 거부, 해당 계정의 모든 Refresh Token 삭제, 재로그인 요구
- Refresh Token이 없거나 형식이 올바르지 않음 → 재발급 거부, 재로그인 요구

## USR-AUTH-007 비밀번호 재설정 요청

**트리거**
비밀번호 찾기 화면에서 이메일과 아이디를 입력하고 재설정을 요청한다.

**사전조건**
없음(비로그인 상태에서도 요청할 수 있다).

**입력**
- 이메일 (string, 이메일 형식)
- 아이디 (string)

**처리 로직**
- 이메일로 계정을 조회하고, 해당 계정의 loginId와 입력한 아이디가 일치하는지 확인한다.
- 일치하면 CSPRNG로 영문+숫자를 혼합한 6자리 재설정 토큰을 생성해, Redis에 `SET NX EX`로 예약한다(키가 없을 때만 저장 + 30분 TTL 지정을 한 번에 처리하는 원자적 명령). 이미 존재해 예약에 실패하면 새 값을 생성해 재시도하며, 최대 5회 재시도 후에도 실패하면 500 에러를 반환한다.
- 그 토큰을 쿼리 파라미터로 담은 재설정 링크(예: `/reset-password?token=xxx`)를 생성해 해당 이메일로 발송한다.

**출력**
별도 화면 이동 없이 입력 화면에서 인라인으로 "재설정 안내 메일을 발송했습니다. 비밀번호 변경 후 다시 로그인해주세요." 메시지와 로그인 화면으로 이동 버튼을 노출한다.

**예외 케이스**
- 이메일 형식 오류 → 입력 필드에 인라인 에러 표시, 요청을 보내지 않는다
- 이메일·아이디 불일치(존재하지 않는 이메일, 잘못된 아이디, 또는 조합이 맞지 않는 경우 모두 포함) → "이메일 또는 아이디가 올바르지 않습니다" 표시
- SMTP 이메일 발송 요청 실패 → 이메일 입력 필드 아래 인라인 에러 표시, 재시도 가능

## USR-AUTH-008 비밀번호 재설정 완료

**트리거**
이메일로 받은 재설정 링크를 열어 새 비밀번호를 입력하고 제출한다.

**사전조건**
만료·폐기되지 않은 재설정 토큰을 보유하고 있다.

**입력**
- 재설정 토큰 (string, 영문+숫자 혼합 6자리)
- 새 비밀번호 (string, 8자 이상 20자 이하, 영문+숫자+특수문자 조합)

**처리 로직**
- 재설정 토큰이 유효한지 확인한다.
- 유효하면 비밀번호를 새 값으로 변경하고 해당 토큰을 즉시 폐기한다.
- 비밀번호 변경과 동시에 해당 계정의 Refresh Token을 전체 삭제해 기존 로그인 세션을 모두 끊는다.

**출력**
재설정 완료 안내, 로그인 화면으로 이동.

**예외 케이스**
- 재설정 토큰이 만료(30분 경과)됨 → 재설정 거부, 에러 페이지에서 이메일 입력 화면으로 재유도
- 이미 사용되어 폐기된 토큰으로 재시도 → 재설정 거부, 에러 페이지에서 이메일 입력 화면으로 재유도
- 존재하지 않거나 조작된 토큰 → 재설정 거부, 에러 페이지에서 이메일 입력 화면으로 재유도
- 새 비밀번호 형식 오류(8자 미만, 20자 초과, 또는 영문·숫자·특수문자 중 하나 이상 누락) → 인라인 에러 표시("비밀번호는 8-20자의 영문+숫자+특수문자 조합으로 설정해주세요"), 요청을 보내지 않는다

## USR-AUTH-009 아이디 찾기

**트리거**
로그인 화면에서 아이디 찾기를 선택하고 가입 시 사용한 이메일을 입력한다.

**사전조건**
없음(비로그인 상태에서도 요청할 수 있다).

**입력**
- 이메일 (string, 이메일 형식)

**처리 로직**
- 발송 횟수는 `findId:attempts:{email}` 키에 `INCR`로 원자적으로 카운트하며, 발송할 때마다 TTL을 10분으로 갱신한다(슬라이딩). 발송 횟수가 5회를 초과하면 429 에러(`SEND_LIMIT_EXCEEDED`)를 반환한다.
- 이메일로 계정을 조회한다.
- 계정이 존재하면 해당 이메일로 loginId를 발송하고, 이메일 입력 화면에 인라인으로 완료 안내를 표시한다.
- 계정이 존재하지 않으면 이메일 입력 화면에 인라인으로 "해당 이메일로 가입된 계정이 없습니다"를 표시한다.

**출력**
별도 화면 이동 없이 이메일 입력 화면에 인라인으로 결과를 표시한다.

**예외 케이스**
- 이메일 형식 오류 → 입력 필드에 인라인 에러 표시, 요청을 보내지 않는다
- 존재하지 않는 이메일 → 이메일 입력 필드 아래 "해당 이메일로 가입된 계정이 없습니다" 인라인 표시
- 10분 내 발송 횟수 5회 초과 → 429 에러, 10분 후 재요청 유도
- SMTP 이메일 발송 요청 실패 → 이메일 입력 필드 아래 인라인 에러 표시, 재시도 가능
