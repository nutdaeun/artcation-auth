## USR-AUTH-004 로그인

**트리거**
로그인 화면에서 아이디와 비밀번호를 입력하고 로그인 버튼을 누른다.

**사전조건**
- 비로그인 상태다.
- 이메일 인증이 완료된 계정이 존재한다.

**입력**
- 아이디 (string)
- 비밀번호 (string)

**처리 로직**
- 아이디로 계정을 찾고 비밀번호가 일치하는지 확인한다.
- 탈퇴 상태의 계정은 존재하지 않는 계정과 동일하게 처리한다.
- 인증에 성공하면 Access Token(15분 만료)과 Refresh Token(슬라이딩 만료 2주, 절대 만료 60일)을 발급해 httpOnly·Secure·SameSite=Lax 쿠키로 내려준다.

**출력**
로그인 성공, 홈 화면으로 이동.

**예외 케이스**
- 존재하지 않는 아이디, 비밀번호 불일치, 또는 탈퇴한 계정 → "아이디 또는 비밀번호가 올바르지 않습니다" 표시, 어느 경우인지 구분하지 않는다
- 계정 정지 처리: 정지 정책 자체가 아직 논의되지 않아 이번 범위에서 제외한다(추후 필요 시 정책 확정 후 반영).

## USR-AUTH-005 로그아웃

**트리거**
로그아웃 버튼을 누른다.

**사전조건**
로그인 상태다(유효한 Access 또는 Refresh Token을 보유한다).

**입력**
없음(쿠키의 토큰으로 세션을 식별한다)

**처리 로직**
- 현재 세션의 Refresh Token을 서버에서 즉시 삭제한다.
- 클라이언트의 Access·Refresh Token 쿠키를 만료시킨다.

**출력**
로그아웃 처리, 홈 화면으로 이동.

**예외 케이스**
- 이미 만료되었거나 무효화된 토큰으로 요청 → 오류 없이 로그아웃 상태로 처리한다(멱등 처리)

## USR-AUTH-006 Access Token 재발급

**트리거**
Access Token 만료로 API 요청이 거부된 클라이언트가 Refresh Token으로 재발급을 요청한다.

**사전조건**
만료·폐기되지 않은 Refresh Token을 쿠키로 보유하고 있다.

**입력**
- Refresh Token(쿠키)

**처리 로직**
- Refresh Token이 유효한지, 이미 사용되어 폐기된 토큰은 아닌지 확인한다.
- 유효하면 새 Access Token과 새 Refresh Token을 발급하고 기존 Refresh Token은 즉시 폐기한다.
- 직전에 폐기된 토큰이 교체 후 30초(유예시간) 이내에 다시 사용되면, 동시 요청·네트워크 재시도로 보고 세션을 유지한 채 재발급만 거부한다(새 토큰을 발급하지 않는다).
- 이미 폐기된 토큰이 유예시간이 지난 뒤 다시 사용되면 탈취로 간주해 해당 계정의 모든 Refresh Token을 삭제한다.
- 동시에 같은 Refresh Token으로 여러 요청이 들어오면 하나만 재발급에 성공하고, 나머지는 유예시간 이내 재사용으로 처리한다.
- 최초 로그인 시점 기준 절대 만료 60일이 지났으면, 슬라이딩 만료가 남아 있어도 재발급을 거부한다.

**출력**
새 Access·Refresh Token을 쿠키로 갱신.

**예외 케이스**
- Refresh Token이 슬라이딩 만료(2주)를 지남 → 재발급 거부, 재로그인 요구
- 절대 만료(60일)를 지남 → 재발급 거부, 재로그인 요구
- 교체 후 30초 이내 직전 토큰 재사용(동시 요청·재시도) → "이미 갱신된 토큰입니다" 409, 세션 유지, 이미 갱신된 쿠키로 원래 요청을 다시 보낸다(로그아웃 처리하지 않는다)
- 유예시간이 지난 폐기 토큰의 재사용(탈취 의심) → 재발급 거부, 해당 계정의 모든 Refresh Token 삭제, 재로그인 요구
- Refresh Token이 없거나 형식이 올바르지 않음 → 재발급 거부, 재로그인 요구

## 참고: 다른 기능과의 연동 (USR-AUTH-008 비밀번호 재설정 완료)

비밀번호 재설정 기능 자체는 이 발췌본의 범위가 아니다. 다만 토큰 정책과 맞물리는 부분만 옮겨 둔다.

- 비밀번호 변경과 동시에 해당 계정의 Refresh Token을 전체 삭제해 기존 로그인 세션을 모두 끊는다.
